# 26.1 Porting Primer For Hemomancy

This primer distills the HutosLib 1.21.1 -> 26.1.x port into a reusable baseline for Hemomancy. Treat the Hemomancy port as a staged rewrite, not a version bump: toolchain, registries, generated resources, data storage, item models, rendering, UI, particles, networking, and custom gameplay data all changed enough to deserve explicit passes.

Baseline used for this primer:

- Minecraft `26.1.2+`
- NeoForge `26.1.x`
- Java `25`
- HutosLib branch `neo-26.1.2`
- HutosLib as the compatibility foundation for Hemomancy

## Porting Areas

### Toolchain And Project Baseline

- Move Gradle/MDK, wrapper, run configs, mod metadata, CI, and Java toolchain to the 26.1 shape before touching gameplay.
- Use Java `25`; do not keep older source or target compatibility.
- Keep client, server, and datagen runs separate and verify each one early.
- Expect generated metadata and generated resources to participate in normal builds.

### Registries, Identifiers, And Bootstrap

- Use `Identifier` in current mapped code where old code used `ResourceLocation`.
- Build ids before object construction when 26.1 APIs require registry ids in properties.
- Prefer NeoForge deferred register helpers for blocks and items; avoid hand-registering block items during raw register events.
- Put item entries, not raw block entries, into creative tabs.
- Fix bootstrap crashes before resource work. `Block id not set` and unbound registry values usually mean registration order or id-in-properties is wrong.

### Datagen And Resource Formats

- Split data generation into `GatherDataEvent.Client` and `GatherDataEvent.Server`.
- Generate client models and language on the client event; generate recipes, loot, and tags on the server event.
- Replace old model-provider pairs with the current `ModelProvider` pattern.
- Generate 26.1 client item definitions under `assets/<modid>/items/*.json`.
- Keep baked model JSON under `assets/<modid>/models/**`; item definitions point at baked models or special models.
- Use `RecipeProvider.Runner` for recipes.
- Convert recipes to current JSON shape:
  - Ingredient item: `"minecraft:stick"`
  - Ingredient tag: `"#minecraft:planks"`
  - Result key: `id`, not old `item`
- Generated recipes, tags, loot, language, blockstates, and item definitions should become canonical once datagen is stable.

### Data Components, Attachments, And Persistence

- Audit every custom `ItemStack` NBT path and move stack state to data components where it belongs.
- Keep component values immutable; set or update the component after mutation.
- For banner-like item state, store vanilla components such as `DataComponents.BASE_COLOR` and `DataComponents.BANNER_PATTERNS`.
- Use `ValueInput` and `ValueOutput` for 26.1 persistence code.
- Register serializable attachments with `AttachmentType.serializable(...)` and implement `ValueIOSerializable`.
- Do not trust login-only sync for player attachments. Sync on join, login, respawn, dimension change, and tracking as appropriate.
- Client packet handlers should tolerate early entity lookup misses for the receiving player.

### Networking

- Use `CustomPacketPayload` plus `StreamCodec`.
- Register payloads once through `RegisterPayloadHandlersEvent`.
- Choose the correct direction for every packet: clientbound, serverbound, or bidirectional only when both directions are real.
- Duplicate payload ids now fail loudly. Keep packet registration centralized.
- Snapshot mutable values, especially `ItemStack`, when constructing sync packets.
- For reload data and progression sync, define one full-state sync path before layering incremental sync.

### Items, Tools, Weapons, And Armor

- Rebuild tools and weapons around 26.1 item properties and components rather than old tier constructors.
- Audit old durability, mining speed, repair, enchantment, ability, and attack behavior.
- Use current tool, weapon, attack range, damage type, and use-effect components where they fit.
- Recheck armor and worn visuals against the current equipment and render-state APIs.
- For Hemomancy weapons, port behavior first with simple visuals, then restore advanced rendering after item definitions and datagen are stable.

### Client Item Models And Special Renderers

- Do not debug purple/black inventory icons until `assets/<modid>/items/*.json` exists for every item.
- Use generated plain or handheld item definitions for ordinary items.
- Use `ItemModelUtils.specialModel(...)` for dynamic item visuals that cannot be expressed with vanilla dispatch, tint, select, range, or composite item models.
- Register special item renderers with `RegisterSpecialModelRendererEvent`.
- Implement `SpecialModelRenderer<T>` when stack data matters; use `NoDataSpecialModelRenderer` when it does not.
- Keep authored baked base models and textures for transforms, particles, and model geometry.

### Entity, Block Entity, And Player Rendering

- Port renderers to the 26.1 render-state pipeline.
- Copy runtime entity data into render-state data through render-state modifiers and `ContextKey`s.
- Submit geometry with `SubmitNodeCollector` rather than old immediate rendering paths.
- For player layers, store copied stack data in render state, then read only the render state in the layer.
- For block entity renderers, use `BlockEntityRenderer<T, S>` with a render-state object.
- In `extractRenderState`, copy block entity state and resolve item stack render state with `ItemModelResolver`.
- In `submit`, transform and submit copied render states only.

### Screens, Menus, And Guide-Style UI

- Port screens from old render methods to `extractRenderState`.
- Use `GuiGraphicsExtractor`.
- Replace old draw calls with current methods:
  - `drawString` -> `text`
  - `blit` -> `blit(RenderPipelines.GUI_TEXTURED, ...)`
  - `renderFakeItem` -> `fakeItem`
  - `renderComponentTooltip` -> `setComponentTooltipForNextFrame`
- Update old mouse and key signatures to the current event types.
- Keep UI layout fixes separate from API-port fixes where possible; 26.1 rendering changes can hide layout bugs.

### Particles And Visual Helpers

- Replace old custom `ParticleRenderType#begin` and custom `RenderType` assumptions with 26.1 particle groups and layers.
- Port particles to `SingleQuadParticle` or `SimpleAnimatedParticle` where appropriate.
- Implement `getGroup()` and `getLayer()`.
- Update particle factories to the current provider signature and register providers through `RegisterParticleProvidersEvent#registerSpriteSet`.
- Keep custom lightning or beam helpers isolated so Hemomancy effects can reuse HutosLib helpers later.

### Recipes, Reload Data, And Gameplay Systems

- Port custom recipe serializers before restoring custom recipe JSON.
- For crafting results that modify components, prove the returned stack carries the modified components before debugging rendering.
- Port book, ritual, skilltree, or progression reload listeners after packet basics are stable.
- Treat data reload sync as a multiplayer feature: test dedicated server, integrated server, reload, join, and reconnect.
- Keep old shadow/helper reload code behind a small compatibility surface where possible.

## Hemomancy First Pass Checklist

1. **Build/toolchain:** update Gradle, NeoForge, Minecraft, Java `25`, metadata, CI, and run configs.
2. **Registries and ids:** port identifiers, deferred registers, item/block properties, creative tabs, menus, particles, attachments, and serializers.
3. **Datagen/resources:** restore generated recipes, tags, loot, lang, blockstates, baked models, and client item definitions.
4. **Components/persistence:** move stack NBT to data components, port saved data and attachments to `ValueInput`/`ValueOutput`, and define full sync paths.
5. **Networking/sync:** register every payload once, set packet direction explicitly, snapshot mutable data, and test reconnect plus tracking.
6. **Items/tools/weapons/armor:** port core gameplay behavior before advanced visuals; audit repair, enchantment, use, attack, range, damage, and ability behavior.
7. **Ritual/world/reload data:** port ritual recipes, world state, progression, reload listeners, and datapack resources after core packets compile.
8. **Client item models/rendering:** generate item definitions, then restore special item models, entity layers, BERs, and dynamic visual effects.
9. **Screens/particles/special effects:** port menus, guide-like screens, tooltips, input handlers, particles, beams, and overlays to current APIs.
10. **Runtime smoke tests:** run datagen twice, build, client, dedicated server, multiplayer join, world reload, and gameplay checks for every core item and ritual path.

## Lessons From HutosLib

- Missing inventory icons were not texture bugs until 26.1 client item definition JSON existed.
- Datagen stabilization paid for itself; it prevented recipe, tag, loot, language, blockstate, model, and item-definition drift.
- Custom renderers were easier to restore after normal model output loaded cleanly.
- `builtin/entity` item models are not a useful long-term bridge for 26.1 custom item rendering.
- Player attachment sync needs more than login sync. Join, respawn, dimension change, and tracking are separate lifecycle edges.
- Packet handlers should handle local-player timing gracefully when the target entity id is not yet resolvable.
- ItemStack packet payloads should copy stacks before encoding.
- Guide UI bugs were mixed API and layout issues; isolate API porting first, then tune UVs, text bounds, colors, and hover behavior.
- Arm banner crafting proved the order: first make the stack components change, then make item rendering see them, then make worn rendering see synced state.
- Server startup must remain a first-class check. Client-only screens, renderers, model layers, and particle factories cannot leak into common/server paths.

## HutosLib Helper Surfaces To Prefer For Hemomancy

These helpers do not all need to exist before Hemomancy starts, but Hemomancy should consume helpers where HutosLib already has a stable pattern:

- Identifier helpers for namespaced ids, textures, GUI paths, and entity texture paths.
- Component helpers for common stack state reads, writes, copies, and tooltip output.
- Packet registration helpers for `CustomPacketPayload`, `StreamCodec`, direction, and duplicate-id prevention.
- Datagen/model helpers for plain item definitions, handheld items, special item definitions, and recipe output.
- Attachment helpers for `ValueIOSerializable`, full-state sync, tracking sync, and login/respawn/dimension lifecycle sync.
- Rendering helpers for special item models, player render-state data, BER state extraction, GUI extraction, and common particle submission.

## Acceptance Checks For A Porting Pass

- `.\gradlew.bat compileJava --continue`
- `.\gradlew.bat runData`, then run it again and confirm stable generated output.
- `.\gradlew.bat build --continue`
- `.\gradlew.bat runClient`
- `.\gradlew.bat runServer`
- Scan `run/logs/latest.log` for HutosLib or Hemomancy entries containing:
  - `Couldn't parse data file`
  - `Missing item model`
  - `Missing textures`
  - `Invalid path`
  - `Missing block model`
  - duplicate payload registration
  - client-only class loading on the server
- In-game smoke checks should cover crafted stack components, inventory/hand/world rendering, equipped rendering, GUI screens, particles/effects, reload data, save/reload, reconnect, and multiplayer tracking.
